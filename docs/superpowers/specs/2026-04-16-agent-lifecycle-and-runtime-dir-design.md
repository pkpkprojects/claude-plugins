# Agent Lifecycle Management & Runtime Directory Redesign

**Date:** 2026-04-16
**Status:** Implemented
**Scope:** dev-flow plugin

## Problem Statement

Two issues in the current dev-flow pipeline:

1. **Stale agents** — Implementers and reviewers that finish their tasks remain active for the rest of the pipeline (sometimes hours), consuming resources. Shutdown only happens at pipeline end (Step 7.3). The orchestrator should proactively terminate agents that are no longer needed.

2. **Runtime artifacts in `.claude/`** — Review outputs and reports are stored in `.claude/dev-flow/reviews/`, which conflicts with the principle that `.claude/` is for configuration, not runtime data. Multiple parallel sessions (without git worktrees) can overwrite each other's artifacts.

## Design

### 1. Agent Lifecycle Management

#### Mechanism: Post-Task Need Check

After every `TaskUpdate(status: "completed")` from an agent, the orchestrator performs a **need check**:

```
Agent completes task
    ↓
Orchestrator inspects PIPELINE_STATE:
    - What tasks remain in the current phase?
    - What phases remain in the plan?
    - Does any remaining task match this agent?
    ↓
Match found → Assign next task (SendMessage to existing agent)
No match   → Shutdown agent (SendMessage shutdown_request + free slot)
```

#### Matching Rules

The orchestrator decides based on:

1. **Agent type** — implementers get implementation tasks only, reviewers get review tasks only
2. **Context affinity** — an implementer that worked on module X is a better candidate for the next task on module X than a fresh agent
3. **Task availability** — if all remaining tasks are blocked (blockedBy), and the agent won't be needed when they unblock → shutdown

#### PIPELINE_STATE Addition

```
active_agents: [
  { id, type, name, current_task, assigned_since }
]
```

The orchestrator updates this list on every spawn and shutdown.

#### NEED_CHECK Procedure (added to Phase 3)

After receiving a completed task from an agent:

1. Fetch remaining tasks (`TaskList`)
2. Filter tasks matching the agent's type
3. If unblocked tasks exist → assign the best match (`SendMessage`)
4. If only blocked tasks exist → check if agent will be needed when they unblock
   - Yes → agent waits
   - No → shutdown
5. If no tasks remain for this agent type → shutdown

### 2. Runtime Directory `.dev-flow/`

#### Session ID

Generated by the orchestrator at pipeline start: `YYYYMMDD-HHMMSS-XXXX` (timestamp + 4 random hex chars). Stored in `PIPELINE_STATE` and passed to agents via their prompts as `SESSION_DIR`.

#### Directory Structure

```
.dev-flow/                              # .gitignore'd, runtime only
└── {session-id}/                       # unique per pipeline run
    ├── reviews/
    │   ├── phase-1-security.md
    │   ├── phase-2-acceptance.md
    │   └── ...
    └── reports/
        ├── pm-final-report.md
        └── legal-review.md
```

Configuration remains unchanged:
```
.claude/dev-flow/
├── config.yaml
└── review/
    └── checks.yaml
```

#### .gitignore

`session-start.sh` adds `.dev-flow/` to the project's `.gitignore` if not already present. Session directories (`.dev-flow/{session-id}/`) are created by the orchestrator at pipeline start, not by the hook — the hook doesn't know the session ID.

#### "Save to docs?" Flow

When an agent generates a report that may have lasting value:

1. Agent writes report to `.dev-flow/{session-id}/reports/`
2. Agent informs orchestrator: "Report X ready, may be worth preserving"
3. Orchestrator asks user: "Legal review saved to `.dev-flow/{session-id}/reports/legal-review.md`. Save permanently to `docs/`?"
4. If yes → copy to `docs/` and commit
5. If no → stays in `.dev-flow/`, cleaned up with the session

#### Cleanup

- **After phase completion:** orchestrator removes `.dev-flow/{session-id}/reviews/phase-N-*`
- **After pipeline completion:** orchestrator removes `.dev-flow/{session-id}/` entirely
- **Stale sessions (safety net):** `session-start.sh` removes session directories older than 24 hours
